# SQLite P3d Entity UX and implementation checkpoint

P3a–P3c remain the accepted baseline. The Codex interaction model can be adapted to vault-scoped SQLite without changing EntityReference semantics or Document persistence. **One transaction-policy conflict needs a decision before implementation:** the accepted P3d plan permits a committed Entity when linking subsequently fails; the new brief requires failed create-and-link without orphan Entity state. No production code has changed during this checkpoint.

## Codex Entity UX inventory

## P3d implementation boundary

The existing [plan §12](MUTABLE_SQLITE_PERSISTENCE_P3_APPLICATION_COMPOSITION_PLAN.md#12-original-entity-scope-and-the-recommended-decision) proposes injected, vault-scoped canonical Entity services, stable supplied identities, optimistic revisions, native annotation Undo and no legacy fallback. That remains suitable except for the creation/link failure policy identified below.

| Concern | Proposed bounded implementation |
|---|---|
| Application capability | Resolve from the selected source Document's verified canonical identity and persistence/vault context. Never use the last-focused Window or implicitly create a default Entity database. Unbound/ambiguous context is explicitly unavailable; existing native assertions remain intact. |
| Production components | Add a narrow Entity service contract and application adapter; inject it into `entity-references/index.tsx`, `search-view.tsx` and the existing summary-loader seam. Add bounded typed worker operations, host routes and SQL service tests using the existing `client.mjs`, `worker-entry.mjs`, foundation and vault leases. Extend current native annotation/search capabilities only for a demonstrably necessary atomic replacement command. |
| Canonical state | SQLite `Entity`, `EntityAlias` and `Relationship` remain canonical per vault. Existing GUID/revision columns, uniqueness rules, worker ownership, read-only checks and backup mechanisms are reused. Names are not unique identity keys. |
| Reference state | Native `codex/entity-reference` properties/linked annotation definitions store the Entity GUID and native ranges. Prose supplies surface text. Any stored `entityName` is a display snapshot, not canonical-name authority. Unsaved changes remain in the repository and its History until ordinary Resource Save. |
| First link | Initial canonical name is selected text. A separate query/name field supports another name without changing the mention. Validate selection before dispatch and again before annotation. Stable-ID lookup/create and explicit partial outcomes depend on the transaction decision below. |
| Aliases | Explicit add/update/remove with stable alias identity, origin and optimistic revision; curated/imported aliases require database backup. Observed mention forms are presented as evidence, not silently inserted into `EntityAlias`. An observed-origin record is only rebuildable when backed by surviving authoritative text/provenance. No automatic alias extraction is added here. |
| Relationships | Explicit source Entity GUID, type and target Entity GUID with validated endpoints, stable Relationship GUID and optimistic revision. Creating two EntityReferences does not create a Relationship. No graph canvas or broad relationship-management UI. |
| Identity and deletion | Linking, unlinking, name/alias edits, Resource relocation and multiple occurrences never change Entity GUID. Unlink/Undo changes native assertions only. General Entity deletion is deferred: absence of saved SQL references cannot prove absence of live, unavailable or out-of-scope references. |
| Recovery | Full native Resource files recover authored references; database backup recovers exact canonical names, enrichment, curated/imported aliases and explicit Relationships. Rebuilding saved projections must not replace canonical records. Missing legacy GUIDs remain unresolved, never merged by name or fabricated from mention strings. |
| Audit | Reuse the existing `PendingAuditMutation` foundation with an explicitly bounded policy for canonical writes. Mutations and their outbox entries belong to one SQLite transaction; reject further writes if the chosen bound cannot be honored. Audit delivery remains separately scoped; no claim that this makes editor/file writes transactional with SQLite. |
| Legacy dependencies | Current lookup/create/summary calls route to `server/entity-search.ts` and SurrealDB; its Alias query actually searches historical mention text. Replace those dependencies for this Entity feature with the injected SQLite capability. No `entities.json`, SurrealDB fallback or automatic legacy migration. Other historical server facilities are not indiscriminately removed. |
| Query coverage | Preserve native live-over-saved mention composition and P3b proofs. Local counts are scoped live counts; vault counts carry coverage. Unknown must not appear as zero, and SQL Entity writes must invalidate affected read proofs without blessing unrelated stale saved state. |

P3a–P3c defaults, coordination and authority remain unchanged. An Entity-service switch must be independent of saved-query rollout, default on under the standing new-feature rule, and fail closed when unavailable. Disabling it must not silently resume legacy canonical writes after SQLite has become authoritative.

## Transaction policy requiring a decision

The accepted plan states: **“An Entity may have committed when selection becomes stale; do not delete it automatically or claim a cross-store transaction.”** The new brief asks for **“failed create-and-link without orphan Entity state”**, cancellation without canonical mutation, and safety across restart/reopen.

The current code demonstrates the gap directly:

1. [`search-view.tsx`](src/features/entity-references/search-view.tsx) awaits server Entity creation, then invokes `chooseEntity`.
2. [`chooseEntity`](src/features/entity-references/entity-search.ts) separately checks the repository revision and commits the native annotation.
3. Cancel or editing can close the panel during the request; a late completion is deliberately ignored. Existing tests prove **no late annotation**, not **no committed server Entity**.
4. Native Resource Save is a later resource-owned filesystem operation. Neither the worker's SQLite transaction nor the native paired-save receipt includes the other authority or the live repository History transaction.

Changing request order does not remove the failure window. Creating first can leave an Entity when the annotation fails. Linking first can leave a reference to an Entity that was never committed. Deleting an Entity as compensation is unsafe once another Document/client may reference it, and a lost response or browser crash cannot reliably trigger that compensation. Holding a SQLite transaction across browser interaction also cannot atomically commit unsaved repository state or later file publication.

**Recommendation:** retain independently committed canonical Entity creation with explicit outcomes: `not created`, `created and linked`, `created but not linked`, and `creation outcome unconfirmed`. Retry a known attempt with the same GUID, revalidate the new selection, and never auto-delete or blindly create a replacement identity. Cancellation before dispatch creates nothing; after dispatch it cannot promise rollback. Undo removes the reference, not the Entity. This requires explicit acceptance because it does not meet a strict reading of the new no-orphan requirement.

If strict all-or-nothing recovery is required, stop for a bounded design of staged Entity publication and durable intent/recovery tied to native Document persistence. Define whether success means a live annotation or a durably saved annotation before implementing that design. Existing saved Facts, saved-only deletion guards and the audit outbox are not substitutes for this missing coordination contract.

Exercise database backup/restore for canonical knowledge separately from rebuilding file-derived projections. Stop after the P3d report; no P6, Save optimization, compatibility Open or new file-format work.
