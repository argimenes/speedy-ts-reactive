# Vault Content Recognition Strategy

**Current correction — 3 October 2026.** SQLite P3a–P3d are closed and accepted. The subsequent manual-acceptance directives authorize physical browsing, content-based Document recognition, format-based Save/source binding, and LER access for verified Documents. The latest clarification establishes Vaults as Mutable platform services, consumed by Flint and other applications. The bounded implementation and its acceptance evidence are recorded in [the correction report](MUTABLE_VAULT_ACCEPTANCE_CORRECTION_REPORT.md); existing paired persistence retains its own protocol. They supersede the earlier import-first and blanket read-only compatibility proposals. Markdown generation, new serialization formats and cross-vault knowledge exchange remain outside this correction. The [accepted architecture](docs/architecture/PERSISTENCE_AND_HISTORY.md#mutable-vault-platform-boundary) records the platform boundary; P3a-era sequencing below is historical, not a new implementation gate.

The selected directory defines browsing scope. Generic `.json` is a candidate, not a Resource type. Validated content must select an existing Document codec and admission path. No canonical identity rule requires `.mutable.json` as a suffix; the current restrictions largely combine discovery, recognition and native pair enrollment. Those concerns should be separated.

This clarification supersedes any suggestion that legacy JSON must remain invisible or be renamed to become eligible for recognition. It does not turn unrelated JSON into a Document or authorize bypassing native identity, ownership, confinement or caller-baseline checks.

## Mutable Vault ownership and establishment

A Vault is a filesystem root associated with one Mutable system directory and one vault-scoped persistence/knowledge context. Mutable owns root establishment, confinement, recognition/admission, verified source binding and canonical Entity/Relationship services. Flint, Ink, Phosphor and Tack consume those capabilities. Application selection and disposal govern presentation leases, not whether a Vault exists.

Reuse the existing `<root>/.mutable/` convention, including `mutable.db` and `audit.db`. The databases' existing schema and vault identity validation remain authoritative for opening that infrastructure. Do not add a Flint database, system directory, global enrollment catalog or second hierarchy. Existing pair archives and relocation records retain their meanings; they are not evidence that each containing subdirectory is a separate Vault. Hide Mutable infrastructure in ordinary browsing.

Physical containment defines a file's vault scope independently of suffix, recognition or SQL enrollment. Recognition determines whether it is a Document and which codec can round-trip it. Verified canonical identity and source binding determine which operations that Document can perform. A database row alone proves none of these. The destination for canonical Entity operations is the unique verified source Vault, never a selected tab, last-focused Window or default database.

The development default is the configured managed Documents root, currently this repository's `data` directory, exposed to the managed API as `.`. `/data` in the product brief denotes that root; it must not become a scattered absolute filesystem literal. Use one platform configuration/composition setting. Missing, unreadable or overlapping defaults surface a reason and the existing selection flow; do not silently choose a different canonical knowledge database. Notes/Ideas remain unsaved and unbound until explicit Save.

### Non-overlap is a durable platform invariant

Vault roots must not overlap, including established Vaults without active application leases. Opening the same valid root reuses its existing identity/context; closing a Window or releasing the last lease does not make a nested Vault legal. There is no nearest-Vault-wins rule and no automatic migration, merge or deletion of conflicting infrastructure.

The implementation now places persistent topology checks in `src/knowledge-sqlite/vault-scope.mjs`, shared by the worker host and direct foundation/restore entry points. The application read model retains only an early UI check; the platform remains authoritative after all leases close. The existing per-Vault writer lock remains distinct from establishment coordination.

The shared establishment/open check follows these rules:

1. Resolve a confined real directory with the existing symlink/path rules. Browsing a folder is not automatically establishment of a new persistence scope; valid subfolders of a Vault remain ordinary folders.
2. Check active root reservations and inspect `.mutable` evidence in ancestors up to the filesystem root. Ancestor inspection reads only the exact system-directory evidence; it grants no authority to browse or write outside the configured managed root.
3. Inspect descendants with explicit entry/depth/time limits. Do not follow symlinks. Check system-directory evidence in hidden directories too; do not hide a child Vault by applying the Document-browser filter. Once conflicting evidence is found, reject without enumerating the child Vault's contents.
4. Treat any ancestor/descendant `.mutable` evidence as a conflict or an explicit invalid/ambiguous state. Permission failure, a symlink relevant to the scope proof or a scan budget limit means **scope not established**, never proof of no child Vault. Arbitrary dormant descendant detection requires traversal; the bounded rule is to refuse establishment when that traversal cannot finish reliably.
5. Serialize check-and-establish with a purpose-specific, per-user OS advisory lock (`mutable-vault-establishment-<uid>.lock` in the OS temporary directory). It coordinates cooperating server/CLI processes across proposed roots; it is not a catalog or a lock on ordinary filesystem operations. The host holds it across scope inspection and worker startup/establishment, then releases it. The asynchronous host uses bounded retries; direct synchronous tooling reports busy explicitly. Per-Vault writer locking still governs the subsequent worker lifetime. Direct foundation/restore entry points use the same coordinator; no application UI decides lock ownership.
6. At the exact requested root, reuse a valid existing system directory/database. Missing, partial, malformed or mismatched existing infrastructure is unavailable/recovery-required, not permission to initialize a replacement database and lose canonical knowledge. A genuinely new root may initialize using the qualified foundation path.
7. Surface explicit conflict/incomplete/unavailable results through any application/API caller. Revalidate when starting a fresh platform context; discovered descendant conflicts also make ordinary discovery incomplete. Do not claim a bounded point-in-time check prevents arbitrary concurrent external filesystem changes; retain that limitation without adding watchers or a global catalog.

Only lightweight root/scope verification belongs in this correction, not general filesystem indexing. A synchronous whole-tree walk on every Entity request is not the intended implementation. Establishment must produce usable scope evidence, with conservative invalidation, and retain existing request-level source/currentness checks.

### Qualification and current concerns

Test same-root reuse across two applications/Windows; active and dormant ancestor/descendant rejection after release and restart; sibling Vaults; path aliases and symlinks; malformed/partial system directories; denied or incomplete traversal; concurrent parent/child creation; direct API/foundation/restore bypass prevention; and inspection-only foundation opening without initialization (not a server product mode). Rejection must create no second database. Exercise source-bound LER against two distinct Vaults to prove focus/selection cannot redirect Entity writes. The historical Document edit/save/LER/reopen gate below remains required.

A read-only inspection on 3 October 2026 visited 106 entries under the configured `data` root, found no `.mutable` directories there or in its ancestors, and encountered no truncated scan or symlink uncertainty. This is provisional filesystem evidence, not a concurrency guarantee or proof that the new guard is implemented. No system directory or database was created by that inspection.

No conceptual conflict prevents this architecture. The concrete implementation risks are dormant-root detection, cross-process check/create ordering, and distinguishing a new root from incomplete existing infrastructure. The focused platform tests cover those cases. The subsequent user correction removes deliberate read-only server mode: normal Mutable composition is writable. Filesystem, SQLite, identity, scope and currentness failures remain operational errors, never permission to bypass validation. Internal database inspection/backup read handles and fault-test adapter guards are not a separate Mutable product mode.

Separate Vaults intentionally retain separate canonical knowledge contexts. Explicit Entity/Alias/Relationship import or merge is future work requiring identity/conflict/provenance and recovery rules; none is implemented here. The supplied clarification ends mid-sentence in that future-work section. Its current Vault requirements are complete enough to apply without inventing the missing text.

**Markdown export clarification:** generated Markdown is deferred and is not a default requirement for this compatibility work. A recognized Document must be browsable and openable without a `.md` sidecar or enrollment in paired export. Do not create a Markdown file during inspection/Open, or make implementing a new projection naming convention a prerequisite for compatible Document access. Native authored bytes remain authoritative. Existing enrolled pairs retain their receipt, conflict and recovery protections; this clarification does not authorize discarding their evidence or ignoring a pending operation. Any later change to their Save behavior must be explicit and separately qualified.

## Accepted persistence direction after P3a review

Browse → Recognize → Admit → Save capability → Index are distinct decisions. For a historical format with an existing safe, qualified writer, the intended path is to open, edit and save the same file in that format. Compatibility must not become permanently read-only merely because the suffix is old. If no safe writer exists, report that specific unavailable capability; do not invent conversion during Open or Save.

A future native `.ink` Document is complete and authoritative by itself. Recognition, identity, admission, editing, authoritative Save and SQLite indexing must not require `.ink.md`. Missing optional Markdown is not a pending or incomplete native Resource. The eventual `.ink.md` is disposable/regenerable export, not a jointly authoritative half of Document identity. No export is generated by inspection/Open. Production generation, projection receipts and any migration remain deferred.

Existing enrolled `.mutable.json` + `.md` resources remain a separate compatibility case with their qualified receipts, generations, recovery, relocation and conflict protections. Those protections are preserved until their transition is explicitly designed and qualified. They must not be copied into the new `.ink` model as a requirement for an optional projection.

Filesystem Resources remain authoritative for authored content. SQLite is the persistent database/knowledge/index destination, with canonical Entity/Alias/Relationship transition separately gated at P3d. SurrealDB and JSON database stores such as `entities.json` are legacy providers, not target persistence. Any future SurrealDB graph computation would be optional and ephemeral over SQLite-derived data. This direction does not authorize P3d implementation in the foreground-coordination follow-up.

The foreground-lock correction changes none of these recognition/admission decisions. It continues to use the existing format and pair adapters; it does not yet implement compatibility Open or standalone typed handlers.

## Minimum bounded compatibility change

1. **Browse:** extend the existing confined directory read model with candidate rows for generic JSON and typed resources. No identities are minted during enumeration, and arbitrary JSON does not enter `documents` just because it is visible. Keep folder/path provenance, inspection errors and pending operations. Do not add a parallel catalog.
2. **Recognize on explicit Open:** read bounded regular bytes through managed confinement, then classify known envelope discriminators and supported Document-root forms. Run the existing strict codec/validator for that format; recognized-but-invalid native/History data must not fall through to a permissive legacy decoder. Workspace/typed resources must dispatch to their handler or return a bounded unavailable-handler result.
3. **Admit:** dispatch native bytes to native admission, History Documents to the supported History path, and legacy Codex Document trees to their existing Document path. Require stable authored Document/resource identity, preserve ownership and duplicate/conflicting identity behavior, and reuse a valid canonical source rather than importing a new copy on every click. Reject missing identity when safe canonical admission would otherwise require minting it. Runtime occurrence/Cell keys are not new Resource identities.
4. **Retain source and explicit capabilities:** keep source filename/format/hash provenance. Inspection/Open does not rename, rewrite, produce Markdown, create a new save generation, flatten native resources, or treat a legacy source as an implicit conversion. Existing supported legacy saving remains format-specific; a native envelope at an unqualified pair location must not silently gain paired-save permission. An unavailable Save capability is explicit rather than triggering conversion.
5. **Index:** let positively recognized supported files participate through their matching P2 adapter. Native identity comes from native bytes, not path. Keep recognized-source evidence, persisted SQL profile, ambiguity, current scope fences and positive absence checks. Do not infer sidecar identity from a same-stem `.md`. Preserve unresolved definitions and unknown authored payloads.

For modern `.ink`, reuse the native codec and qualify source recognition/admission independently of export. Production binding support remains a compatibility change, but `.ink.md` generation is deferred and must not block Open. When generated projections are introduced later, the earlier `.ink`/`.ink.md` proposal must be applied consistently to pairing, collisions, receipts, relocation and recovery, without migrating existing `.mutable.json` + `.md` pairs implicitly. If only read compatibility is qualified first, state that explicitly. Opening `.ink` must not be implemented by inventing `.mutable.json` file paths or rewriting the file.

## Invariants exposed by relaxing suffix gates

There is no suffix-based canonical identity invariant to preserve. The real constraints are:

- Native `.mutable.json` currently selects the paired persistence route; the Markdown filename is mechanically derived by replacement in several locations. Applying that replacement to `paper.json` can produce the same filename rather than a safe sidecar. Blindly deleting suffix checks would therefore be incorrect.
- Qualified discovery and selected Open compare resource identity, hashes, binding location, pair receipts and pending relocation evidence. A content-recognized file still needs the appropriate evidence; SQL cannot provide or adopt its binding.
- Generic JSON includes unrelated graph/Entity seeds, Workspace envelopes, malformed files and historical copies with repeated IDs. A positive supported-format result is different from uncertain inspection and from a conclusive non-Document result. The latter must be based on content, with unknown reserved formats remaining unavailable rather than guessed. P2's conservative reconciliation behavior remains until those classifications and their deletion/uniqueness consequences are qualified.
- Existing native Workspace guards remain. Opening a compatible legacy Document must not become a reason to flatten native registered resources through Workspace tree persistence.

## Placement in current work and qualification

Continue the already-authorized P3a host/coverage and workload characterization without changing its P2 correctness oracle. Record compatibility opening as a bounded prerequisite before claiming broadly usable saved-vault consumers in P3b/P3c. The native-only scope in the P3 composition plan describes the current provider qualification; it is not the intended permanent vault browsing model.

The user-visible compatibility gate must include `poe-raven.json`, another real supported historical JSON Document, unrelated JSON, malformed/unknown-version JSON, a native envelope under a generic JSON filename, `.mutable.json`, `.ink`, and the three typed presentation extensions. Check candidate visibility, correct content dispatch, successful supported Document Open, unsupported/unavailable-handler outcomes, unchanged file hashes, unchanged identities, duplicate rejection, confinement/symlinks, repeated Open, editability and explicit Save capability. Run compatible Document cases without Markdown sidecars and assert that inspection/Open creates none. Test both direct click and saved-result navigation when the latter is enabled. Typed-handler scenarios remain explicitly blocked where that handler has not been implemented; do not claim the complete mixed-vault scenario passes today.

This updates the strategy without introducing a new codec, generic JSON authoring format, migration-on-Open or automatic Entity authority change. P3a still stops at its existing review gate before P3b.
