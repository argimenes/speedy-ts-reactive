# Flint Stage C implementation plan

**Architecture accepted. Stage A, Stage B and native Save/Open production integration are complete. C1a and C1b are accepted. C2 and the SurrealDB infrastructure review are accepted. C3 is implemented; see the [C3 qualification report](FLINT_C3_QUALIFICATION_REPORT.md) for the integrated Stage C review gate. No later stage is authorized.**

Stage C makes Flint a knowledge workspace over canonical Documents: browse and organize a real managed directory, create Documents, edit native tags/properties, find passages, create/follow native references and see backlinks. Stage A supplies independent transient occurrences; Stage B supplies native fidelity and resource-owned Save/Open. The editor remains ordinary Codex.

A vault is a selected directory within the existing managed server document store, including when that server runs locally. It is not an arbitrary browser filesystem handle or an Obsidian compatibility layer. Opening it reconstructs folders and Document locations from the directory tree. There is no second folder-assignment or membership system. **Safe pair and directory relocation is the bounded C1 persistence extension**, replacing its previous deferral; the accepted save protocol otherwise remains intact. Native Workspace round-trip, tab restoration and generalized synchronization remain outside Stage C.

## Identity and organisation

| Concept | Authority and behavior |
| --- | --- |
| Physical location | Actual vault directories and filenames. Renaming/moving a Document relocates its `.mutable.json` and sibling `.md` pair and updates the resource's persistence binding. |
| Document identity | Canonical resource ID inside native bytes, independent of path, title, folder and occurrence. Duplicate IDs at distinct locations are ambiguous, not two new Documents. |
| Semantic classification | Native tags/properties. Tags are many-to-many and provide the first cross-folder organization through a simple tag filter. No virtual folders. |
| Semantic relationships | Authored native references using stable Document/Block identities. Moving files does not rewrite these identities. |
| Derived organization | Directory listings, search, backlinks and later saved views. No authoritative membership list or sidecar index/database is needed to restore the hierarchy. |
| Ownership and retention | Existing authored ownership and non-owning resource registration. A filesystem parent directory does not become a semantic resource owner. |

Document title and file stem are separate controls: “Edit title” changes native authored metadata; “Rename file” changes the pair's physical names. No implicit title rewrite accompanies relocation. Closing a tab or vault affects presentation/query scope, not canonical ownership, retention or an in-flight save. Filesystem actions are explicit storage operations, not entries in Document Undo/Redo. Native text/title/tag edits retain ordinary Undo/Redo. Deletion, resource destruction and filesystem Trash are deferred; the former virtual Trash/membership-removal proposal is removed rather than reinterpreted as deletion.

## C1 Filesystem vault and Document properties

C1 has two qualification gates because the requested filesystem model adds a real storage operation. Review the relocation proof before enabling its production UI.

### C1a Directory discovery and relocation proof

**Discovery.** Select one managed directory; enumerate actual subdirectories, including empty ones, and native resources. Use bounded/cancellable traversal and expose permission, size-limit, malformed-file and incomplete-scan diagnostics. Read validated native identity from file contents, not filenames; the ID-to-location map is an ephemeral scan result. Opening the vault does not admit every Document into the repository. Revalidate bytes/identity through the existing Open path when a Document is opened, and do not resolve duplicate IDs arbitrarily. Operations requiring unique identity must wait for a complete bounded scan of the selected vault or fail explicitly; an incomplete listing is not evidence of uniqueness.

Treat a confirmed native/Markdown pair as one Document row. Native files without enrollment evidence remain visible, but paired save/move requires the existing explicit enrollment and collision checks. Standalone `.md` files are explicit import sources, never authoritative Documents merely because they are newer. An unrelated same-stem `.md` must not be silently claimed as a projection. Hide managed recovery/lock archives from ordinary Document enumeration; show their operational status separately. Other files may be shown as unsupported assets; do not import, rewrite or silently delete them.

The same normalized managed root opened in two Flint Windows shares a tree scope and canonical resources, with independent occurrences. Initially reject overlapping/nested active vault roots and cross-vault/cross-filesystem moves; neither is necessary to prove one managed vault. The user can reselect the root after restart and reconstruct organization without saved Workspace state. Any remembered root path is a convenience, not hierarchy authority.

**Minimum relocation extension.** Add a resource-owned rename/move operation taking the source binding, resource ID, exact caller native/Markdown baseline, destination and idempotent operation ID. Restrict initially to a confirmed enrolled pair with no pending save/conflict; finish or recover that save first. Move existing confirmed bytes, not a fresh capture. Unsaved canonical edits may remain in memory and must remain dirty; serialize Save and relocation so a queued save uses the confirmed new binding. Occurrence closure must not cancel or misattribute the operation.

1. Under a stable managed-store lock outside movable subdirectories, validate source identity, hashes/generation, source location authority and destination absence. All affected native writers/recovery routes must honor this lock and any pending relocation; applicable legacy routes must not bypass native guards. Lock ordering must be fixed. Check both public filenames, pair-evidence locations, path confinement, case/Unicode aliases, symlinks, file/directory collisions and move-into-descendant errors. Never merge or overwrite an occupied destination.
2. Durably record a bounded relocation intent before changing paths: operation ID, resource ID, source/destination, reviewed baseline, evidence needed to recognize the actual files and progress. Keep operation records at a fixed managed-store recovery location so moving a folder cannot strand its journal. These are operation/recovery records, not a hierarchy manifest or database; directory discovery must work without consulting completed records for membership.
3. Preserve the actual source files/inodes and existing pair archive while publishing at the destination with create-only/no-replace semantics. Verify after each transition; retain displaced or conflicting data for recovery, including late writes through old handles. Never implement this as unchecked `rename` calls or copy-and-delete that discards external writes. Do not claim two-file atomicity. Surface “Relocation pending” and block conflicting Open/Save until the operation is resolved.
4. Transition the active pair receipt/location evidence to the new names; retain immutable old save intents, captured bytes and archives. Preserve the content generation and hashes. Return a verified binding transition to update the resource session, existing location associations and dependency lookup. Add only the location revision/fencing evidence necessary to reject stale-location requests, including rename-away-and-back; a content hash alone is insufficient. Compatibility with existing receipts/baselines must be qualified, with legacy callers failing closed when a location fence is needed. Do not alter native wire bytes or the Workspace schema.
5. Recover by operation ID after transport loss or server restart, inspecting the journal and actual files at both locations. Replay only proven steps; never overwrite unexpected content, infer success from filename presence alone or silently refresh an editor's content baseline. Keep conflicts explicit and all evidence available. After completion, stale clients at the former location receive a relocation/conflict response, not permission to recreate the resource there. Retention/cleanup policy beyond existing conservative archive retention stays deferred.

Exact journal names and fields remain provisional. Reuse existing staging, hashing, locking and recovery helpers where valid; do not force relocation into a save intent whose contract assumes fixed filenames. **A no-replace and external-write-preservation primitive must be demonstrated on the supported host. If it cannot be implemented within this bounded adapter, stop with that concrete limitation before enabling relocation.** No new durability claim is implied.

**Directories.** Create actual directories exclusively after confinement/collision checks. Rename/move a directory as a directory, preserving its contents, empty descendants and pair archives; do not reconstruct it from a list of Documents. Preflight a bounded affected subtree, reserve source/destination, block on pending pair operations or unenrolled native pairs requiring explicit enrollment, and record all affected resource bindings for recovery. A completed directory move updates descendant location associations without recapturing Documents or recursively generating Markdown. Unsupported/symlink entries or uninspectable subtrees block the move explicitly. Unrelated ordinary files move unchanged. Directory no-replace behavior, interference during the operation and recovery are part of C1a's proof; one filesystem rename does not make all client binding updates atomic.

**External changes.** Refresh on Open Vault, explicit Refresh, window refocus and before mutation; no watcher/polling/synchronization subsystem is required. Reconcile additions, removals and renames into the tree without discarding dirty live content or unloading resources. Revalidate scan observations on action; scans are not an atomic filesystem snapshot. A vanished source becomes “location missing,” not a new empty Document. A unique same-ID file elsewhere is a candidate location, not automatic authority: explicitly reconcile only with unchanged reviewed native/Markdown bytes and verified pairing evidence, or report a conflict. An external rename may leave receipt filenames or archives behind; report/repair that only through the qualified reconciliation operation. Partial pair moves, duplicate IDs, changed bytes and ambiguous archives remain blocked. Markdown modification never promotes it to canonical state.

**Markdown links and dependencies.** The current exporter emits path-based wiki links. Preserve existing paired bytes during relocation; native references stay valid, but previously exported incoming links may become stale. Report this limitation and refresh locator mappings for subsequent explicit saves, including a user-requested projection refresh through a fresh paired save from one immutable capture. That refresh may create a new save generation even when native bytes are unchanged; relocation itself does not regenerate the projection. Do not automatically rewrite every referring file or promise complete Markdown link repair. Owned resources keep independent identities and authored ownership; moving a folder is not a multi-resource content transaction. Rebuild dependency locations from verified vault discovery/registrations, validate decoded IDs and retain failure for missing owned dependencies. Resources outside the vault still require existing explicit location resolution; no general discovery service.

**Gate C1a:** demonstrate fresh-process tree reconstruction without membership metadata; empty/nested folders; pair grouping and standalone Markdown; missing/malformed/duplicate identities; read-only and unsafe paths. Prove same-directory pair rename, cross-directory pair move and nonempty directory move, preserving native and Markdown bytes, canonical IDs, pair recovery and dependency semantics. Test either filename/archive collision, case-only rename policy, unsupported cross-device move, concurrent saves, stale clients, rename-away-and-back, lost response and actual server restart at each meaningful phase. Inject external replacement, creation, deletion and late writes; verify preserved files and explicit conflicts. If case-only rename needs an intermediate path, it must use the same journal, not an unrecorded workaround. Produce recovery evidence and review before C1b; substantial storage redesign remains a stop condition.

### C1b Flint vault UI and native properties

Expose Open Vault/Refresh, the real folder tree, New Document in the selected folder, explicit Markdown import, directory create/rename/move, and pair rename/move through the qualified service. Creating a Document establishes one canonical candidate outside the Window, then saves the pair at a collision-checked destination. A failed first save leaves a clearly unsaved candidate, not a completed tree entry. Adding an already-bound Document to another directory means an explicit supported relocation, not logical membership or an implicit copy. Moving an existing binding from outside the selected vault remains deferred; open its containing vault instead.

Provide editable native title and string-list tags, a simple tag filter, and read-only ID/format/location/save status. Reuse an existing tag field if available; otherwise add one bounded native metadata field with ordinary Undo/Redo and unknown-payload preservation. Tags may overlap freely across folders. No arbitrary property schema or saved-view engine. Tag filtering covers available loaded Documents initially and exposes incomplete coverage for unopened resources.

**Gate C1b:** exercise real UI/server routes with two Windows on one vault: create/save, title/tag edits and filters, pair rename/move, directory move, continued typing during relocation, close/reopen occurrences and reopen the vault after restart. Confirm shared canonical content/history, independent focus, dirty edits retained, updated Save destination and unchanged reference targets. Prove title-only edits do not rename files and file moves do not rewrite titles. Reopen native resources with unrelated authored payloads intact; verify read-only behavior, explicit import collisions, dependency failure and the existing Workspace/legacy bypass guards. Rerun Stage A/B/native regressions. No deletion/Trash, automatic native Workspace restoration or transfer of semantic ownership is authorized.

## C2 Search and native reference navigation

The directory tree defines vault scope; the initial text/tag queries and default backlinks implementation cover only its loaded, available native resources, whether or not they have tabs. Distinguish unopened files from complete results and allow explicit Open before rerunning a query. Directory discovery itself does not require repository admission or hidden editors. A future whole-vault disk index is not part of C2/C3.

Deliver title/text search over the loaded, available native resources discovered in the selected vault, result snippets and navigation into a passage. Include Documents with no mounted occurrence. Traverse canonical authored content once per vault resource; respect separate Document boundaries and do not follow external resource bodies merely because a reference exists. Foreign/transcluded bodies outside that scope and unsupported hosted text must be diagnosed rather than silently counted as complete coverage. Reuse supported native text extraction and worker matching; no duplicate editor, hidden mount or Markdown export as a search source.

Start with plain text search and the existing matcher defaults. Bound/cancel work and invalidate stale generations when text, directory discovery or vault scope changes. Reuse monotonic content epochs so Undo followed by a new edit cannot make old offsets appear valid. An action on a result revalidates identity and revision, opens/reuses a tab in the invoking Flint Window, then reveals the current range. Never focus another occurrence just because it was the first match.

Add a Document picker for creating a reference from a nonempty valid text selection within one Document. Use the existing annotation transaction and selection restoration; do not depend on typing Markdown. Creation, removal and Undo/Redo must use native annotation semantics. Opening an existing Document reference resolves the canonical ID/root Block ID and uses the same navigation action as search. Existing unsupported reference forms remain authored and are reported rather than rewritten into the new picker subset.

**Gate C2:** find text in a loaded vault Document with no tab; count a Document once despite multiple occurrences; exclude resources outside the vault and diagnose unopened, missing or ambiguous resources. Test Unicode and inline images, query replacement/cancellation, edits and Undo branches during search, external file removal or relocation during a query, and stale result activation. Create a reference, Undo/Redo it, rename its target, follow it from either Window, and verify correct focus/selection and source disposal. Reopen the native file and follow the same stable target. Search/navigation alone must not mutate native bytes or add history entries.

Stop if querying unmounted canonical content requires a second editor, persistent search index, broad input changes or substantial projection reconstruction. A small extraction adapter is justified; a new search platform is not.

## C3 Derived backlinks and integrated qualification

Preimplementation inspection: [existing Node/SurrealDB infrastructure review](FLINT_SURREALDB_INFRASTRUCTURE_REVIEW.md). The legacy Entity/text index is not a current native-reference backend; the review recommends retaining the bounded canonical default below. The review is accepted. C3 uses the bounded canonical service below; it does not modify, repair, migrate or reindex SurrealDB.

Deliver a narrow, read-only backlinks service and a Flint Backlinks view that consumes it through the application capabilities. The contract asks which authored references point to a stable Document/Block target within an explicit vault scope. It must not expose standoff storage, repository traversal or a database query language to Flint. Stage C exercises Document targets; it does not add a broader Block-navigation UI.

The minimal contract supplies:

- Stable source/target identities and a source-mention locator, with labels/snippets sufficient for display. No DOM nodes, projection keys or live editor objects cross the boundary.
- Explicit coverage and freshness information, including unopened or unavailable resources, unsupported reference forms and partial or stale results. An empty partial result must not claim that no backlinks exist.
- Cancellable asynchronous queries and disposable change notifications. A delayed response for an old target, scope or generation must not replace the current view.

Core navigation revalidates a returned locator, opens/resolves the intended occurrence and reveals its current source range using C2's navigation action. The backlinks service owns neither focus nor editor occurrences, canonical resource lifetime or persistence. Supply it directly through the existing host composition; no service locator, backend registry or provider-selection UI is required.

Provide one default implementation using explicit native Document references authored in loaded, available native resources discovered in the vault. Resolve linked annotation definitions through existing ownership/provenance helpers. One linked mention with multiple segments is one mention; separate mentions remain separate. Multiple tabs do not duplicate counts. Ignore deleted annotations, presentation `documentTarget` descriptors, structural ownership, filesystem containment, Find highlights and Entity annotations. Unrecognized reference forms are not guessed into Document backlinks. The abstraction hides how references are found, not their semantic meaning.

Use a bounded canonical scan initially, with invalidation of affected resource entries and coalesced refresh while the view is active. Reference creation/removal, linked definition changes, text/range edits, title changes, Undo/Redo, directory discovery changes, relocation and source disappearance must invalidate relevant results. Closing the panel disposes its subscription and pending queries without cancelling another consumer's work. No full-repository snapshot on each keystroke, polling, observers on editable DOM or background graph framework.

A later local index or application-database implementation may satisfy the same semantic contract while declaring its coverage and freshness. Neither is implemented or qualified in Stage C; backend consistency, synchronization and indexing policy remain outside this plan. No additional authored relationship format or persistence contract is needed for the default implementation.

**Gate C3:** qualify the service separately from Flint's UI, and use a small delayed/partial-result test double to demonstrate that the UI depends only on the contract. Check cancellation, disposal, stale completions and visible incomplete coverage; do not build a second production backend. Default-service results must match the declared reference subset and loaded scope; duplicates, deleted mentions, unresolved/foreign definitions and cyclic references behave deterministically. Following a backlink revalidates and reveals the correct source mention in the invoking Window. Reference removal and Undo/Redo refresh results without stale rows. Rebuilding the derived view yields the same results and never changes canonical state.

Complete one real-browser workflow: create two Documents in real subdirectories, rename/move a pair and folder, edit title/tags, create and follow a reference, search a passage in an unmounted loaded Document, follow a backlink, refresh after an external directory change, save/reopen both native files, and repeat with two Windows. Inspect the UI and keyboard/focus behavior. Run focused vault/query/reference tests, the accepted Stage A/B/native regression suites and inexpensive Grouping, Entity, IME and native-control smoke checks. If query subscriptions change the typing path, compare the existing typing benchmark and verify no repository snapshot is introduced for ordinary typing; no exhaustive viewport/theme matrix is required.

## Approval and completion boundary

Current boundary: **C3 implementation and integrated qualification → Stage C review**. C1a, C1b and C2 are accepted; C3 implementation and qualification are recorded in its report. These are bounded gates within Stage C, not permission to start later roadmap stages. Each report should identify implementation changes, qualification results and any unmet scope assumptions. New Stage C features default on when implemented, under the existing feature conventions.

Stage C is complete when the bounded filesystem-vault workflow works through ordinary native editing, with useful search/references/backlinks and honest persistence/scope limits. Keep the accepted remaining persistence boundaries as future work: native Workspace round-trip, cross-vault/cross-filesystem relocation, archive cleanup, synchronization, broader Markdown and additional platform durability. Graph visualization belongs to a later roadmap stage. C1a infrastructure and C1b vault UI/native properties are accepted. C2 search/reference navigation is accepted. C3 backlinks and integrated qualification are complete for review. Their reports retain the supported-host behavior and conservative rejection boundaries. Stop for Stage C review.

## Separate future work: native-derived SurrealDB ingestion

Begin from the accepted [infrastructure review](FLINT_SURREALDB_INFRASTRUCTURE_REVIEW.md), not the assumption that legacy Text/Entity rows already represent native references. A future adapter must establish canonical resource/Block identity, generation and freshness evidence (including unsaved state), deletion/reconciliation, native Cell boundaries, linked-definition provenance and deterministic relationship identity. It may satisfy the current backlinks service contract only while declaring truthful coverage and rejecting stale navigation. SurrealDB remains derived and rebuildable; canonical identity, ownership, persistence binding, save generation and live unsaved state remain authoritative outside it. No ingestion, migration, repair, bulk reindexing or cleanup is included in C3.
